# 支付可靠性加固设计

## 目标

在不修改商品价格、支付宝商户渠道、现有付费遮罩和现有用户权益的前提下，解决“用户已经付款，但支付回调丢失后积分不到账”的核心问题，并同步补齐支付订单持久化、重复回调幂等、电脑二维码、第三方超时、接口滥用、生产密钥和合盘订单保存方面的可靠性缺口。

## 范围

本次包含：

- 积分包和月度会员的漏回调主动补偿。
- 积分、会员、八字报告和合盘报告的统一支付订单台账。
- 数据库唯一约束与原子到账。
- 缺失的 `report_orders` 表及相关索引。
- 电脑端二维码本地生成，手机端支付宝跳转保持不变。
- 支付平台请求超时、有限重试和稳定错误响应。
- 下单与查单接口限流。
- 生产环境密钥缺失时失败关闭。
- 新合盘订单的服务端记录和登录用户归属。

本次明确不包含：

- 不改变现有前端付费遮罩方式。
- 不将报告正文迁移为服务端生成。
- 不改变商品价格、商品数量、支付平台或支付方式。
- 不追溯重建无法可靠确认的历史合盘订单。

## 现状与约束

- 当前积分到账依赖支付平台异步回调；`check-order` 只查本地积分记录，不会向支付平台补查。
- 八字报告已有支付平台主动查单补偿，但代码依赖的 `report_orders` 在当前项目配置连接的 Supabase 中不存在。
- 当前数据库中已检查 2069 条积分订单和 180 条会员订单，未发现重复 `order_id`，可以安全设计唯一索引迁移，但迁移前仍须重新检查。
- 支付平台签名算法和现有 MD5 规则保持兼容；所有业务判断继续以服务端固定商品目录和固定金额为准。
- 所有数据库变更必须向后兼容，不删除、不覆盖现有积分、会员或历史支付记录。

## 方案选择

采用统一订单台账方案，而不是仅在 `check-order` 中临时补一段积分发放代码。

统一订单台账记录每次由本站创建的订单及其可信业务上下文。支付平台回调和浏览器轮询只能确认支付状态，不能从浏览器请求中决定商品、金额、用户或渠道。两条确认路径最终调用同一个幂等履约入口，因此无论先收到回调、先完成轮询，或两者并发发生，都只会发放一次权益。

## 数据模型

### `payment_orders`

新增统一支付订单表，至少包含：

- `order_id`：主键，本站生成的订单号。
- `product_code`：服务端商品目录中的稳定代码。
- `product_type`：`credits`、`monthly`、`bazi_report` 或 `hepan_report`。
- `amount`：下单时由服务端写入的固定金额。
- `user_id`：登录用户编号，游客为空。
- `channel`：经过长度和字符校验的渠道标识。
- `metadata`：报告键、报告参数、标签等必要业务信息。
- `status`：`pending`、`paid` 或 `fulfilled`。
- `created_at`、`paid_at`、`fulfilled_at`。

`order_id` 必须唯一。支付状态只能单向从 `pending` 进入 `paid/fulfilled`，重复确认返回既有结果。

### 现有权益表

- 为 `user_credits.order_id` 添加唯一索引。
- 为 `user_subscriptions.order_id` 添加唯一索引。
- 创建缺失的 `report_orders`，其 `order_id` 为主键。
- 所有唯一约束在创建前执行只读重复检查；若发现重复，停止迁移并人工核对，不自动删除数据。

### 原子履约函数

在 Supabase 中增加服务端专用 RPC。它在一个数据库事务内完成：

1. 锁定对应的 `payment_orders` 行。
2. 校验订单仍可履约。
3. 按商品类型写入积分、会员或报告权益。
4. 将订单标记为 `fulfilled`。
5. 返回同一笔订单已有或新生成的权益结果。

数据库唯一约束作为最后防线，保证并发回调和轮询不能重复发放。

## 支付流程

### 下单

1. 浏览器提交商品代码、报告必要参数、登录令牌和渠道。
2. 服务端从固定商品目录决定名称、金额和权益，忽略浏览器提供的金额。
3. 服务端验证登录令牌、渠道和报告参数。
4. 先创建 `payment_orders` 待支付记录；报告订单同时保存可恢复的报告身份信息。
5. 再向支付平台下单。
6. 支付平台下单失败时保留失败前的待支付订单供审计，不授予权益，并允许用户重新创建新订单。

### 异步回调

1. 验证支付平台签名、商户号、支付成功状态、本站订单号和实付金额。
2. 从 `payment_orders` 读取可信商品上下文，不从订单号前缀或回调查询参数决定权益。
3. 调用统一原子履约函数。
4. 已履约订单直接返回成功；暂时性数据库错误返回失败状态，让支付平台继续重试。

### 浏览器轮询补偿

1. `check-order` 先读取本地订单状态。
2. 若已履约，直接返回权益。
3. 若仍待支付，服务端向支付平台主动查询。
4. 仅当平台返回订单号、成功状态和金额均与本地订单完全一致时，调用同一个原子履约函数。
5. 因此即使异步回调完全丢失，积分、会员和报告仍可在轮询时到账。

### 游客与登录用户

- 登录订单的 `user_id` 只来自已验证令牌。
- 游客积分订单返回兑换码，继续支持现有使用方式。
- 登录用户的积分和报告直接绑定账号。
- 新合盘订单写入统一台账和报告订单；历史合盘本机记录继续兼容，但不伪造历史服务端购买记录。

## 二维码与移动端

- 手机端继续使用支付平台返回的支付宝跳转地址。
- 电脑端优先使用支付平台提供的可信二维码图片；若平台只返回付款内容，服务器在本地生成二维码数据，不再把付款地址发送给 QuickChart。
- 前端只展示服务器返回的图片或本地生成结果，不把支付 API 地址误当作二维码内容。
- 二维码失败时保留订单号和手动查单入口，不自动创建多个重叠订单。

## 超时、重试与限流

- 支付平台下单和查单使用明确超时；仅对网络错误、超时和可重试的 5xx 响应进行有限重试。
- 不对已明确返回业务失败的请求盲目重试。
- 同一浏览器请求只保留一个进行中的订单创建动作。
- 下单按客户端标识和用户标识限制频率；查单按订单号和客户端限制频率。
- 限流失败返回明确状态，不改变订单或权益。

## 密钥与验签

- 生产环境必须提供 `PAY_PID`、`PAY_KEY` 和 `TOKEN_SECRET`，缺失时相关接口失败关闭。
- 开发和测试环境可以显式注入测试密钥，但不使用可预测的生产默认值。
- 回调除签名外同时校验商户号、订单号、状态和金额。
- 比较签名和令牌签名时使用恒定时间比较。

## 兼容性与发布顺序

1. 只读检查数据库重复订单和现有表结构。
2. 备份相关表。
3. 执行只新增表、列、索引和 RPC 的数据库迁移。
4. 验证旧代码在新结构下仍可运行。
5. 部署新代码。
6. 使用测试订单验证正常回调、漏回调轮询补偿、重复回调和重复轮询。
7. 观察错误日志与待处理订单，再决定是否清理长期未支付订单。

数据库迁移必须先于依赖新表的代码发布；代码回退时新增表和索引保留，不需要回滚数据结构。

## 测试要求

- 测试先行，每个行为先出现预期失败，再编写实现。
- 覆盖正常回调到账、回调完全丢失后的轮询补发、回调与轮询并发、重复回调、金额错误、订单号错误、商品不匹配和数据库暂时失败。
- 覆盖游客兑换码、登录积分、会员、八字报告和合盘报告。
- 覆盖电脑二维码本地生成和手机支付宝跳转。
- 覆盖支付平台超时、重试上限和限流。
- 保留并运行现有支付、报告、账户和完整站点测试。

## 中断保护

- 设计、数据库迁移、后端订单台账、积分补偿、二维码和安全加固分别提交。
- 每个提交均能通过对应测试，不提交半成品。
- 数据库迁移脚本先进入仓库，未经发布步骤不自动执行。
- 在全部验证完成前不推送主分支、不改线上数据库。
- 任意中断后可从最后一个通过测试的提交继续。
