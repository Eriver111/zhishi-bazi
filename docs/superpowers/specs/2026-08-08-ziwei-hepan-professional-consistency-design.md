# 紫微与合盘专业一致性修复设计

## 目标

修复紫微排盘的输入归一化、晚子时、真太阳时跨日、命身宫字段和专业展示错误；让八字合盘与个人排盘使用完全相同的四柱、旺衰和喜用忌结论；处理当前两项八字专业回归测试。支付、订单、报告解锁及用户存档逻辑不在本次范围内。

## 方案选择

采用“单一专业数据源”方案：紫微只保留 `iztro 2.5.8` 为正式排盘引擎，在调用前统一校验并归一化输入；八字合盘只读取 `BaZiCalculator` 生成的命盘和 `getProfessionalReportFacts()` 生成的专业事实。页面层不再重复判断宫位、旺衰或喜用忌。

不采用以下方案：

- 页面局部修补：改动较少，但继续保留重复算法，后续仍会漂移。
- 重写紫微或八字引擎：范围过大，无法保证不影响现有稳定功能。

## 紫微数据流

1. 页面收集合法公历日期、钟表时间、性别和出生地。
2. 独立的输入归一化模块计算真太阳时，并保留跨日前后的正确公历日期。
3. 23:00 至 23:59 使用 `iztro` 的晚子时索引 `12`；00:00 至 00:59 使用索引 `0`。
4. 将归一化后的日期、时辰索引、性别传给 `iztro.astro.bySolar()`。
5. 页面只读取 `iztro` 正式字段 `earthlyBranchOfSoulPalace` 和 `earthlyBranchOfBodyPalace`。
6. 干支年、阴阳男女、大限和小限等信息优先使用库返回值，不再用公历年份和固定顺行自行推导。

日期必须通过真实月份天数校验。不存在的日期不允许进入排盘。出生地经度无法精确匹配时允许使用现有省级回退值，但页面计算必须保持确定性。

## 合盘数据流

1. 合盘结果页完整读取双方出生地、分钟、真太阳时和子时换日设置。
2. 双方分别调用与个人排盘相同的时间归一化与 `BaZiCalculator.calculate()` 流程，得到 `_bazi`。
3. 每个人只调用一次 `BaZiCalculator.getProfessionalReportFacts(_bazi, gender)`。
4. 合盘旺衰、用神、喜神、忌神以及后续互补和宜忌建议全部消费同一份专业事实。
5. 删除正式路径上的独立 `calcXiyong` 判定；仅在缺少 `BaZiCalculator` 的异常环境中返回明确错误，不静默回退到旧规则。

同一出生参数在个人排盘和合盘中必须得到完全相同的四柱、旺衰等级、用神、喜神和忌神。

## 八字专业回归

- 湿土调整测试以当前专业规则为准，先核查期望值与计分证据；若代码漏算则修代码，若规则已被后续专业修订取代则同步更新测试证据，不能只改数字掩盖问题。
- 天干合化输出统一保留“合而不化”这一专业总类，并在后面补充“隔柱不化”的具体原因。

## 错误处理

- 非法日期、缺失性别、无效时辰在进入排盘库前提示用户并停止。
- 紫微库调用增加异常捕获，失败时恢复页面状态并给出可理解的提示。
- 合盘任何一方无法生成与个人排盘一致的数据时停止分析，不使用简化算法兜底。

## 测试

- 紫微：常规时辰、所有24个钟点标签、23点晚子时、真太阳时前后跨日、春节前干支年、阴阳男女、非法日期、命身宫字段。
- 合盘：参数完整传递、真太阳时和子时换日、同盘四柱一致、专业事实与个人排盘逐字段一致、下游建议使用统一喜用忌。
- 八字：恢复两项现有回归测试，并运行全部非支付测试；最后运行完整测试套件确认未触碰支付行为。

## 变更边界

允许修改紫微页面/脚本、合盘输入/结果/核心脚本、八字专业计算与相关测试。禁止修改 `api/create-order.js`、`api/check-order.js`、支付回调、支付前端、报告解锁和数据库支付表逻辑。本次不推送远程仓库。
