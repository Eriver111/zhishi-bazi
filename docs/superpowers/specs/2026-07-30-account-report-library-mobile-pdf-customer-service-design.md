# 知时账号报告库、移动端 PDF 与客服入口设计

日期：2026-07-30  
状态：已由用户确认采用方案 2  
目标分支：`feat/light-ui-redesign`

## 1. 背景与问题

当前八字深度报告的“永久查看”主要依赖浏览器 `localStorage`：

- 解锁记录只在当前浏览器可靠生效；
- 登录后的云端同步只使用单个 `bazi_rpt` 键，新报告会覆盖旧报告；
- 结果页重新打开时不会先从账号云端恢复全部已购报告；
- 支付回调目前不会为深度报告建立账号级、可长期查询的购买记录；
- 个人中心无法列出已经购买的深度报告；
- 安卓端“保存为 PDF”依赖 `window.print()`，部分安卓浏览器和 WebView 会忽略该调用，表现为进入新页面后点击按钮无反应；
- 客服入口只出现在部分结果页底部，不够容易找到。

## 2. 本轮范围

本轮包含：

1. 登录用户的账号级八字深度报告库；
2. 同账号、同命盘购买一次后长期解锁；
3. 个人中心展示并打开已购报告；
4. 游客仍可购买、当次查看和下载，但不保存到账号；
5. 安卓等移动端直接生成并下载真实 PDF 文件；
6. 个人中心增加所有访客都可见的客服入口；
7. 保留现有积分、排盘记录、游客支付和桌面端导出能力。

本轮不包含：

- 乾造、坤造偶发显示异常；
- 合盘报告库；
- 服务端长期保存 PDF 文件；
- 自动追溯所有历史游客订单；
- 网站其他功能页的结构性改版。

## 3. 核心产品规则

### 3.1 登录用户

- 登录用户购买八字深度报告时，订单绑定当前账号。
- 支付成功后，服务器保存该账号对该命盘的永久访问权。
- 同一账号再次打开同一命盘时，先向服务器查询访问权；已购买则直接解锁，不再展示支付遮罩。
- 个人中心新增“我的深度报告”，列出全部已购报告。
- 点击报告卡片重新进入对应结果页，并由服务器确认访问权。
- 同一账号、同一命盘再次点击购买前，服务端先检查是否已购买，避免重复付费。

### 3.2 游客

- 游客无需登录也能维持当前购买流程。
- 支付成功后保留当前浏览器的本地解锁能力和下载能力。
- 游客报告不进入个人中心，不承诺换设备、清缓存后恢复。
- 页面在付款前用简短提示说明：“登录后购买可在个人中心长期查看；游客购买请及时下载。”
- 游客后续需要恢复时走人工客服，不做自动认领。

### 3.3 报告含义

- 报告库保存的是“访问权＋生成报告所需的标准化命盘参数”，不是一份静态 PDF 文件。
- 重新打开时使用当前网站版本重新渲染相同命盘的报告。
- 报告权永久有效，不继续沿用当前本地记录中的一年过期时间。

## 4. 报告身份与数据模型

### 4.1 标准化报告身份

新增服务端统一的报告身份生成函数。服务端根据所有会影响结果的标准化参数计算 SHA-256 指纹，客户端传入的哈希不作为最终依据。

当前公历/农历排盘至少纳入：

- 年、月、日；
- 时辰、钟表小时、分钟；
- 性别；
- 历法模式；
- 省、市、区和真太阳时相关参数；
- 子时换日选项；
- 其他实际参与排盘计算的参数。

四柱排法上线后还需纳入：

- 年柱、月柱、日柱、时柱；
- 性别；
- 四柱排法模式。

这样可以避免：

- 不同命盘误共享一次解锁；
- 同一参数因顺序不同生成不同指纹；
- 使用当前六位短哈希产生碰撞；
- 客户端伪造一个过于宽泛的报告键。

### 4.2 数据表

新增 `report_orders` 表，以已支付订单作为访问权来源：

- `order_id`：支付订单号，唯一；
- `user_id`：登录用户 ID，游客为空；
- `report_type`：本期为 `bazi`；
- `report_key`：服务端生成的完整报告指纹；
- `report_params`：重新生成报告所需的标准化参数；
- `label`：个人中心展示标题；
- `amount`：实付金额；
- `status`：`pending` / `paid` / `failed`；
- `created_at`；
- `paid_at`。

索引：

- `order_id` 唯一索引；
- `user_id, report_type, report_key, status` 查询索引；
- `user_id, paid_at` 列表索引。

不使用 `user_data.bazi_rpt` 作为新系统的事实来源。它只作为旧版本本地兼容数据保留，不再写入新的报告权益。

## 5. 支付与解锁流程

### 5.1 创建订单

1. 结果页组装完整报告参数；
2. 登录状态下把认证令牌随下单请求发送；
3. 服务端校验令牌并自行生成 `report_key`；
4. 如果当前账号已经拥有该报告，直接返回 `already_unlocked`，不创建支付订单；
5. 否则先写入一条 `pending` 的 `report_orders`；
6. 再调用支付网关并返回二维码或支付链接；
7. 游客订单同样写入订单表，但 `user_id` 为空，不形成个人中心记录。

### 5.2 支付成功

1. 回调先完成签名、订单号、商品类型和金额校验；
2. 对报告订单执行幂等更新，将订单标记为 `paid`；
3. 登录订单从此成为账号访问权；
4. 重复回调不会重复创建或破坏记录；
5. 如果支付回调短暂遗漏，`check-order` 在确认网关已支付后可补做同样的幂等落库，作为恢复路径。

### 5.3 打开结果页

1. 本地游客解锁检查继续保留；
2. 登录用户额外请求服务器检查 `report_key`；
3. 服务器确认存在同账号的已支付订单后，移除支付遮罩并展示下载入口；
4. 网络失败时不误判已购，也不清除本地状态，显示可重试提示；
5. 未登录用户不请求账号报告接口。

## 6. 个人中心

### 6.1 “我的深度报告”

登录后并行加载：

- 积分与购买记录；
- 已保存命盘；
- 已购深度报告。

报告卡片展示：

- 乾造或坤造；
- 出生日期或四柱摘要；
- 购买日期；
- “查看报告”按钮。

列表默认按购买时间倒序。报告权益不提供删除按钮，避免用户误删已购权益；如果以后需要隐藏，可增加仅影响展示的“归档”功能。

### 6.2 客服入口

客服卡片放在个人中心主体内，但不依赖登录状态，因此游客访问个人中心也能看到。

内容：

- 标题：联系客服；
- 微信号：`EriverLife`；
- 一键复制微信号；
- “问题反馈”入口，复用现有反馈接口或弹窗；
- 简短说明：支付、报告恢复、使用异常均可联系。

客服卡片需要比普通说明文字更明显，但不使用自动弹窗，不遮挡主要内容。

## 7. 移动端 PDF 方案

### 7.1 问题根因

当前移动端进入 Blob 报告页后调用 `window.print()`。部分安卓 Chrome 变体、应用内置浏览器和 WebView 不支持或忽略该接口，因此按钮点击无反应。

### 7.2 新流程

桌面端：

- 保留“打开打印页并保存为 PDF”；
- 同时提供真实 PDF 下载作为备用。

移动端：

1. 点击“下载 PDF”后在当前用户手势内启动导出；
2. 把报告克隆到固定 A4 宽度的离屏容器；
3. 按封面和语义区块逐页渲染，避免一次性生成超长画布；
4. 使用本地托管的 `html2canvas` 与 `jsPDF` 生成真实 `application/pdf` 文件；
5. 显示生成进度并防止重复点击；
6. 优先直接下载；
7. 浏览器支持 Web Share Level 2 时提供“保存/分享 PDF”；
8. 两者都不可用时，保留独立 HTML 下载和“使用浏览器菜单打印”的说明作为兜底。

### 7.3 移动端资源约束

- 分页逐张生成，生成一页后释放画布；
- 控制渲染倍率，优先保证文字清晰并避免安卓内存溢出；
- 对超长报告显示进度；
- 导出按钮失败后恢复可点击状态；
- 文件名使用安全的中文标题和日期；
- 依赖文件本地托管，不在导出时依赖第三方 CDN。

## 8. API 设计

新增或扩展：

- `POST /api/create-order`
  - 接收认证令牌和完整报告参数；
  - 生成服务端报告指纹；
  - 写入待支付报告订单；
  - 已购时返回 `already_unlocked`。

- `GET /api/reports/access`
  - 必须登录；
  - 根据标准化参数检查当前账号是否已购。

- `GET /api/reports`
  - 必须登录；
  - 返回当前账号的已购报告列表和安全的重开参数。

- `POST/GET /api/callback` 与 `GET /api/check-order`
  - 对报告订单进行幂等的支付完成落库。

所有账号级查询都只从认证令牌取得 `user_id`，不接受客户端直接指定其他用户 ID。

## 9. 兼容与迁移

- 现有游客本地解锁继续有效，不主动清除。
- 旧版 `bazi_rpt` 云端键不自动转成永久账号权益，因为该键过去可由客户端写入，不能作为可靠付款凭据。
- 新系统上线前的订单如果无法从账号和订单号可靠关联，不自动加入个人中心；用户可凭支付记录联系客服处理。
- 当前积分、会员、兑换码、排盘记录和合盘付费逻辑保持不变。
- 数据库迁移使用 `CREATE TABLE IF NOT EXISTS` 和幂等索引，便于安全重复执行。

## 10. 错误处理与安全

- 创建支付订单前完成参数格式和金额校验；
- 服务端生成报告指纹，客户端不能决定访问范围；
- 回调校验签名、金额、商品类型和订单号；
- 支付落库和查询恢复均幂等；
- 个人中心输出内容做 HTML 转义，避免报告标题或参数注入；
- 不在日志输出完整出生信息、令牌或支付密钥；
- 数据库不可用时，游客当前支付查询仍可返回明确错误，登录报告不得伪装成已永久保存；
- 个人中心报告接口失败时，只影响报告列表，不影响积分和排盘记录展示。

## 11. 测试与验收

### 自动测试

- 标准化参数顺序不同但内容相同，生成相同报告指纹；
- 任一实际影响排盘的参数变化，报告指纹变化；
- 登录用户同一命盘只需购买一次；
- 不同账号不能访问彼此报告；
- 游客支付不会出现在任一账号报告库；
- 回调重复执行不产生重复权益；
- 回调丢失后，订单查询可以补完成；
- 金额或商品类型不匹配时不授予权益；
- 个人中心接口只返回当前用户报告；
- 旧本地解锁仍能工作；
- 安卓导出失败时按钮能恢复并出现兜底入口。

### 浏览器验收

- Windows Chrome/Edge：购买、解锁、刷新、个人中心重开、打印保存；
- 安卓 Chrome：直接下载 PDF；
- 安卓微信或其他 WebView：下载或分享 PDF，失败时显示可执行的兜底方式；
- iPhone Safari：下载/分享 PDF；
- 未登录：客服可见、购买可用、报告不进入个人中心；
- 已登录：客服可见、报告列表可用、换浏览器登录后仍可解锁。

## 12. 上线顺序与回退

建议分两步上线：

1. 先上线数据库表、订单持久化、访问查询和个人中心报告库；
2. 再上线移动端真实 PDF 导出与客服卡片。

回退原则：

- 前端可独立回退到旧支付遮罩和旧导出；
- 新表只新增不破坏旧表；
- 回退时保留已经写入的报告订单，后续恢复新版本仍可继续使用；
- 不删除或迁移现有积分、排盘和本地解锁数据。

## 13. 成功标准

- 登录用户购买一份八字深度报告后，刷新、重新登录或换设备仍可打开；
- 个人中心准确列出该账号全部新系统已购报告；
- 同一账号、同一命盘不会再次要求支付；
- 游客不产生账号报告记录；
- 安卓主流浏览器不再依赖无响应的 `window.print()` 才能保存报告；
- 登录与未登录用户都能在个人中心明显看到客服入口；
- 现有积分、排盘、支付和报告展示不出现回归。
