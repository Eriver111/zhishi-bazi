# 命理事件账本重构规划

状态：第一阶段已实施（只记账、不改结果）；第二、三阶段待按重复类型逐项复核。

## 目标

把旺衰、格局、喜用忌与生克链使用的原局证据统一为一份事件账本，杜绝同一干支关系、同一根气或同一制化链在不同模块被重复加减分，同时保留“先给分、后因受冲折损”这类合理的状态变更。

## 核心原则

1. 每条原局证据生成稳定事件编号，至少包含命盘、来源柱、目标柱、关系类型和作用对象。
2. 同一事件只拥有一份基础力量；旺衰、格局、喜用忌只能引用，不得各自重新计算。
3. 合、冲、刑、害改变证据的有效系数，不凭关系名称重复新增扣分。
4. 区分真正重复与状态追回：月令先得分、受冲后折损属于同一信用的变更，不属于重复扣分。
5. 所有裁决保留结算轨迹，内部审计能够定位原始值、折损原因、最终值和消费模块。
6. 不为单盘设置四柱特判；所有修正必须有同类盘和反例盘回归。

## 分阶段实施

### 第一阶段：只记账、不改结果

- [x] 统一生成天干、地支、藏干、根气、透干有根度，以及五合、六合、六冲、六害、相刑、自刑、三合/半合、三会/半会事件。
- [x] 给现有各评分阶段标注所消费的事件编号。
- [x] 审计层报告同一事件的重复消费候选、相互矛盾和未消费证据。
- [x] 月令先给分、受冲后折损记录为同一信用的状态追回。
- [x] 现有冻结盘保持分数、旺衰、格局和喜用忌零漂移。

实现位置：`js/bazi.js` 的 `buildBaziEventLedger()`，只通过内部
`auditDayMasterStrength()` 返回，不进入普通排盘、AI 上下文或付费报告。
账本中的重复项在第一阶段统一标记为 `candidate`，必须结合具体规则复核后，
才能进入第二阶段去重，禁止看到重复引用就机械删分。
事实层与消费层严格分开：例如现行旺衰算法尚未结算的自刑会保留在事实层，
并进入 `unconsumedEventIds`，不会为了让审计“看起来完整”而暗中新增扣分。

### 第二阶段：处理确定性重复

- 同一对地支的刑害叠扣。
- 同一根气被冲、刑、害多模块重复削弱。
- 同一合局在月令、日支和普通合化环节重复结算。
- 同一透干在旺衰与格局承载中被重复当作独立力量。
- 每类改动单独提交，并配置目标盘、同类盘、反例盘和临界盘。

### 第三阶段：统一力量结算

- 月令信用及受损追回统一化。
- 透干有根度、藏干层级、禄刃长生与根气受损统一化。
- 生克链只引用结算后的有效力量。
- 格局成破与喜用忌读取同一份承载结果。
- 对确有命理依据的冻结盘变化逐盘复核，不批量改写基线。

## 验收标准

- 同一事件不得在同一结论中被重复消费。
- 审计轨迹的总分与主引擎结果完全闭合。
- 旺衰、格局、喜用忌和 AI 上下文不得出现相互矛盾。
- 现有全量测试、冻结盘及新增随机新盘全部通过。
- 任一跨档变化必须能指出唯一规则、明确证据和对应反例护栏。
